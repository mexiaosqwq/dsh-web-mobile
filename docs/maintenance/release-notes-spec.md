# GitHub Release notes 文案规格

发版写 Release notes 时读这份；平时不占会话预算（根 `AGENTS.md` 只留一行触发）。
用户要求（2026-09-20），体例照 v2.4.1 / v2.3.0 定型。**不许直接贴 README 段落**——本档与 README
是两套文本：README「更新内容」段按结果导向一句话写（用户看不懂机制，只看「修了什么」），
Release notes 才写机制与根因（用户是开发者，要能判断「这版要不要升」）。

取材来源：v2.4.1 / v3.0.3 / v3.1.0 三份实发 Release 正文 + README「更新内容」段，逐份对照得出。

## 结构（顺序固定）

1. **标题**：`## vX.Y.Z · 一句话摘要`（Release 的 `name` 字段同此串，不带 `##`）。
   摘要写本版主线，多条用「+」连：`v3.1.0 · 移动端重建批次：顶栏座位重做 + 性能第一批 + 补丁秩序 + C08`。
2. **导语段**：本版是什么 + 桌面 no-op 承诺 + 旧宿主回退建议。按版本身份选一种写法：
   - **普通版**：一两句说清本版主线（`这是 3.1.0 的稳定版。相较 v3.1.0-rc.1，本版闭合了最后一项正确性风险（C08）。`）。
   - **多重身份版**（v3.0.3）：编号列表逐条列身份（修回归 / 落地安全修复 / npm 补发版），
     因为读者要一次看懂「为什么这版值得升」。
   - **补发/合并版**：明说合并了哪些未单独发版的版本（「npm 用户从 3.0.0 直升本版即得全部中间改动」）。
   - **重建/并线版**（v3.1.0）：交代基准（`本版以上游 v3.0.6（b78babc）为权威基准重放本地实现线，未删除上游任何文件`）——
     外部读者最关心「有没有丢东西」。
   - 桌面承诺句式照抄：`桌面端（鼠标指针）行为不变。` / `桌面 ≥1024px / 鼠标指针照旧完全 no-op。`
3. **致谢行**（有外部贡献时必写，位置可在安装前或文末）：
   - 合作人：`特别感谢 @x（PR #63/#65：具体贡献）`
   - 社区贡献与报障逐个列：`@handle（#NN 报障 / PR #NN）`
   - 条目标题带归属：`（#NN by @handle）`
   - **署名从 GitHub 实测取**：PR author + commit author + issue reporter，且只列修复确实落在
     本 tag 区间的。三路核对：close 日期、`closed_by` 提交、`git log vA..vB` 引用。
     未合并的 PR 与仍 open 的报障**不计**。
   - 移植源头单独谢：`感谢 fork wzxmt-zhc 的移植源头`（本仓会话删除三件套即移植自该 fork）。
4. **`### 安装`**：DSHA 一句 + npm 代码块 + GitHub 直装行 + 重启提示。
   固定形态（照 v2.4.1 抄）：

   ```markdown
   [DSHA](https://github.com/qiannianhuanxiang/DSHA) 用户无需单独安装，装 APK 即用。

   ```sh
   dsh plugin --profile web add dsh-web-mobile
   ```

   GitHub 直装：`dsh plugin --profile web add github:mexiaosqwq/dsh-web-mobile`

   仓库自带构建产物，装完重启 `dsh web`。
   ```

   **未发 npm 的版本**（如 v3.1.0）不写 npm 代码块，改 `从本仓库取 dsh-web-mobile（本版未走 npm）`。
5. **`### 新功能`**：新增能力。写清「原来不行 / 现在行」，带触发条件与边界。
6. **`### 修复`**：**三段式**，一条一症状，不许把多条揉进一段：
   `**症状**：<用户看到的现象>。**根因**：<机制层原因>。**修法**：<改了什么>。`
   症状用用户的话（「TPS 读数有时停在旧宽度」），根因用机制的话（「全树观察器从未打开 `characterData`」）。
7. **`### 优化`**（有性能/重构批次时加）：性能条目带**前后读数**（`offsetHeight` 3→0、`rect` 6→0），
   存量盘点也放这里（`!important` 941 → 922、类名子串选择器 658 → 641）。
8. **`### 兼容`**：宿主代际范围（`0.1.7-rc.1` 及以后）+ 已实装验证的第三方版本号 +
   桌面/平板档的实测差异结论（`平板档几何与本批之前逐项 rect 差异为 0`）。
9. **`### 完整提交`**：提交少时逐条 short-hash；大版本列里程碑提交，
   收尾必带 `compare/vA...vB` 完整变更对比链接。
   构建环境无通路时如实交代替代路径（v3.1.0 用 git-data API 在服务端建提交，正文写明原因与提交清单）。
10. **`### 已知未覆盖`**（有未做项时加）：把**没做**的事如实列出并说明为什么不赌
    （`O08 重复选择器收口——已登记留档、未做：选择器是字符串字面量，收敛时一个常量写错即静默失配，
    单测层抓不到；本版之后预算见底，不拿最后一批用户的真机体验去赌`）。
    这条是可信度的来源，**不许为了好看省略**。

## 两条附着规矩

- **README「更新内容」段发版时同步写**（2026-09-25 用户拍板）。版本合并补发时按「上游 tag
  之后所有改动并入本版」口径整理。
- **发布状态口径**：合并 ≠ 可更新。修复合进 main 后用户仍吃不到（npm/Release 还在旧版），
  对外回复必须区分「已合并」与「已发布」，未发版前明说「等下个 release」。

## README「更新内容」段的写法（与 Release notes 分工）

- 版本标题：`### vX.Y.Z (兼容 <宿主代际>)`。
- 首条是**结果导向一句话**概括本版（用户视角，不写机制），其后按 `**新功能**` / `**修复**` 分小节。
- 修复条目只写**现象**、不写根因与修法（机制细节归 Release notes）：
  `状态栏 TPS 读数有时停在旧宽度——纯文本更新唤不醒排版任务`。
- 每条尽量带 issue 号：`（#154）`、`（#149, PR #150）`。
- 兼容代际在首条末尾交代回退建议：`0.1.6-alpha.2 建议维持 3.0.0、0.1.5 之前仍建议 2.4.1`。

## 预发行（rc）也写 Release

`v3.1.0-rc.1` 这类预发行照样发 Release 页——**README 版本段必须覆盖同一版本线的全部 pre-release**：
写某版 README 前先把该版本线每个 tag 页都取回与最高版那页做 diff，pre-release 独占条目要一并写进
（2026-10-13 用户纠错，推定不算数，要 diff）。
