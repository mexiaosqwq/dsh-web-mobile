# GitHub Release notes 文案规格

发版写 Release notes 时读这份；平时不占会话预算（根 `AGENTS.md` 只留一行触发）。

体例在 v2.4.1 / v3.0.3 / v3.0.6 / v3.1.0 四份实发正文上定型，再对齐两类大仓库的机械约定：
Vite 的固定分类词表与「一行一条 + 逐条挂 PR/hash」，GitHub CLI 的「逐条 `by @author in #PR` +
固定 compare 收尾」。刻意保留两处不跟大仓库走——条目留根因（大仓库只写一行，而本仓读者判断
「要不要升」的依据常在根因上），以及「已知未覆盖」一节。

与 README 的分工不变：README「更新内容」段按结果导向写（用户看不懂机制），Release notes 才写
机制与根因（读者是开发者，要能判断这版要不要升）。两套文本不许互相粘贴。

## 结构（顺序固定）

### 标题

`## vX.Y.Z · 一句话摘要`，Release 的 `name` 字段同此串、不带 `##`。摘要是本版主线，多条用「+」连：
`v3.1.0 · 移动端重建批次：顶栏座位重做 + 性能第一批 + 补丁秩序 + C08`。

### 本版必读

标题下第一个小节，1–3 条，一行一条，带链接。只收三种：影响真机体验的、需要用户改配置的、
可能让人不敢升的（破坏性）。够不上标准的版本**不写这节**——凑数比空着更坏，大仓库放这节是
为了让读者三秒内决定升不升。

### 导语

本版是什么 + 桌面 no-op 承诺 + 旧宿主回退建议。按版本身份挑一种写法：

- **普通版**：一两句说清主线（`这是 3.1.0 的稳定版。相较 v3.1.0-rc.1，本版闭合了最后一项正确性风险（C08）。`）
- **多重身份版**（v3.0.3）：编号逐条列身份（修回归 / 落地安全修复 / npm 补发版），读者要一次看懂为什么值得升
- **补发/合并版**：明说合并了哪些未单独发版的版本（「npm 用户从 3.0.0 直升本版即得全部中间改动」）
- **重建/并线版**（v3.1.0）：交代基准（`本版以上游 v3.0.6（b78babc）为权威基准重放本地实现线，未删除上游任何文件`），外部读者最关心有没有丢东西

桌面承诺句式照抄：`桌面端（鼠标指针）行为不变。` / `桌面 ≥1024px / 鼠标指针照旧完全 no-op。`

### 安装

固定形态（照 v2.4.1 抄；DSHA 行按 2026-10-18 更正口径，见下）：

````markdown
[DSHA](https://github.com/qiannianhuanxiang/DSHA) 用户无需单独安装：App 内置的是打包时的快照，本版要等 DSHA 重新拉取源码并发布更新后才带上。

```sh
dsh plugin --profile web add dsh-web-mobile
```

GitHub 直装：`dsh plugin --profile web add github:mexiaosqwq/dsh-web-mobile`

仓库自带构建产物，装完重启 `dsh web`。
````

**未发 npm 的版本**（如 v3.1.0）不写 npm 代码块，改 `从本仓库取 dsh-web-mobile（本版未走 npm）`。
「谁该升、谁留在哪版」写进下面的升级建议表，不在安装段口头带过。

## 正文分类（词表固定）

分类名与顺序固定，按 commit type 派生，**不许临场新造标题**；要加分类先改这份规格。无内容的
分类整节不出现，不留空标题。

| 分类 | 收什么 | 来源 |
| --- | --- | --- |
| `### 破坏性变更` | 宿主代际下线、需用户改配置、需重装迁移 | 有则写，放安装之后的第一节 |
| `### 新功能` | 新增能力 | `feat` |
| `### 修复` | 行为缺陷 | `fix` |
| `### 性能` | 前后读数、存量盘点 | `perf` |
| `### 内部·工程` | 构建/测试/探针/依赖/补丁秩序/文档 | `test` `chore` `build` `docs` `refactor` |
| `### 兼容` | 宿主代际 + 第三方版本 + 桌面/平板档结论 | 固定节 |
| `### 升级建议` | 一眼看懂的通道矩阵 | 固定节 |
| `### 完整提交` | 里程碑 hash | 固定节 |
| `### 已知未覆盖` | 没做的事 + 为什么不赌 | 有则写，不许省 |
| `### 致谢` | 没走 PR 的贡献与移植源头 | 有则写 |

### 条目形态

每条首行一句话说完现象与结论，要交代机制时把根因与修法降级为紧随的缩进子行；纯内部件
（探针、依赖、文档）只写一行。首行给扫版的人，子行给要判断要不要升的人。

```markdown
### 修复
- **侧区纵向滚动被手势层吃掉**：从静止起手时首次滚动失效
  （[#223](https://github.com/mexiaosqwq/dsh-web-mobile/pull/223),
  报障 [#222](https://github.com/mexiaosqwq/dsh-web-mobile/issues/222)
  by @mexiaosqwq / @shuangji66）
  - 根因：轴锁定在判定前就取消了 touchmove
  - 修法：锁定前不再取消，滚动交回原生
```

新功能条目同理，子行写「背景：原来不行」「行为：现在怎样」——读者要的是差别，不是功能清单。

### 逐条归属

每条末尾挂 `（[#PR](url) by @修者）`；有报障时挂成 `（[#PR](url), 报障 [#ISSUE](url) by @修者 / @报障者）`，
跟上面的样例一致。归属一律从 GitHub 现场取，不凭记忆写，三步：

1. `git log --format='%h %s' vA..vB` 拿本版提交清单
2. 从提交信息正则抽 `#NN`
3. 逐条 `gh pr view NN --json number,author` 解析；**解析失败说明它是 issue**——提交信息常写成
   `fix(gesture): …（#222） (#223)`，其中 #222 是报障号不是 PR 号，改走 `gh issue view NN`

实测判例：`（#222） (#223)` 这组里 #222 是 @shuangji66 的报障、#223 是 @mexiaosqwq 的 PR，
两个号都要进条目——缺一个，读者关心的「谁修的」「谁报的」就有一条答不上来。

单提交落地的版本（构建环境到 github.com 无通路时）逐条链接改指 commit hash，正文写明「本版以
单提交落地，逐条指向提交而非 PR」，**不许编不存在的 PR 号**。

### 性能与存量读数

性能条目带前后读数（`offsetHeight` 3→0、`rect` 6→0）；存量盘点也放这节（`!important` 941 → 922、
类名子串选择器 658 → 641）。只写「旧→新」，不写中间过程。

### 兼容

宿主代际范围（`0.1.7-rc.1` 及以后）+ 已实装验证的第三方版本号 + 桌面/平板档的实测差异结论
（`平板档几何与本批之前逐项 rect 差异为 0`）。

### 升级建议

固定四行，每行一句结论；写之前先确认该版实际发到了哪些通道（npm 发了没有、Release 是不是唯一通路）。

```markdown
| 你是什么用户 | 本版建议 |
| --- | --- |
| DSHA（装 APK） | 随 App 更新；DSHA 未重新拉取源码前仍停在旧版 |
| npm 用户 | 本版未走 npm，npm 仍停在 x.y.z |
| GitHub 直装 | 可升，装完重启 `dsh web` |
| 宿主 < 0.1.7-rc.1 | 留在 v3.0.6 |
```

### 完整提交

提交少时逐条 short-hash；大版本只列里程碑提交。构建环境无通路时如实交代替代路径（v3.1.0 用
git-data API 在服务端建提交，正文写明原因与提交清单）。

### 已知未覆盖

把**没做**的事如实列出并说明为什么不赌：

> O08 重复选择器收口——已登记留档、未做：选择器是字符串字面量，收敛时一个常量写错即静默失配，
> 单测层抓不到；本版之后预算见底，不拿最后一批用户的真机体验去赌。

这节是可信度的来源，**不许为了好看省略**。

### 致谢

逐条已经带了归属，这节只收两类：没走 PR 的贡献（对账、验收、讨论）与移植源头
（`感谢 fork wzxmt-zhc 的移植源头`）。有外部合作人时写 `特别感谢 @x（PR #63/#65：具体贡献）`。

**全文最后一行固定收尾**：

```markdown
**完整变更**：https://github.com/mexiaosqwq/dsh-web-mobile/compare/vA...vB
```

## 发版前自查

- 分类只用词表里的：`grep '^### '` 扫一遍正文，出现表外标题就是自创，改回词表或先改规格
- 每条都能点回 PR 或提交，没有裸散文条目
- 每条首行脱离上下文也读得懂（现象 + 结论）；根因不是首行的必要条件，但省略了就只剩 PR 可查
- 性能条目的读数只写「旧→新」
- 「已知未覆盖」如实列，没有就明说没有
- compare 链接对得上本 tag（`vA` 是上一个非 rc 发布，`vB` 是本 tag）

## 两条附着规矩

- **README「更新内容」段发版时同步写**（用户拍板）。版本合并补发时按「上游 tag 之后所有改动并
  入本版」口径整理。
- **发布状态口径**：合并 ≠ 可更新。修复合进 main 后用户仍吃不到（npm/Release 还在旧版），对外
  回复必须区分「已合并」与「已发布」，未发版前明说「等下个 release」。

## README「更新内容」段的写法（与 Release notes 分工）

- 版本标题：`### vX.Y.Z (兼容 <宿主代际>)`。
- 首条是**结果导向一句话**概括本版（用户视角，不写机制），其后按 `**新功能**` / `**修复**` 分小节。
- 修复条目只写**现象**、不写根因与修法（机制细节归 Release notes）：
  `状态栏 TPS 读数有时停在旧宽度——纯文本更新唤不醒排版任务`。
- 每条尽量带 issue 号：`（#154）`、`（#149, PR #150）`。
- 兼容代际在首条末尾交代回退建议：`0.1.6-alpha.2 建议维持 3.0.0、0.1.5 之前仍建议 2.4.1`。

## 预发行（rc）也写 Release

`v3.1.0-rc.1` 这类预发行照样发 Release 页——**README 版本段必须覆盖同一版本线的全部 pre-release**：
写某版 README 前先把该版本线每个 tag 页都取回与最高版那页做 diff，pre-release 独占条目要一并写进
（用户纠错：推定不算数，要 diff）。
